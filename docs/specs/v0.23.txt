Kubio kubio.json v0.23 Specification
Status: Agreed specification
Base: v0.22


1. Scope

v0.23 adds route-level generated responses. A selected route may return a
fixed HTTP response without contacting its upstream. This version covers
fixed responses and redirects expressed through the same response primitive;
it does not add custom bodies for Kubio-generated errors, metrics, new log
sinks or formats, health/admin endpoints, or transport/security policies.


2. Configuration

A route may set `respond`:

    {
      "path": "/maintenance",
      "respond": {
        "status": 503,
        "body": "temporarily unavailable",
        "headers": {
          "Content-Type": ["text/plain; charset=utf-8"]
        }
      }
    }

`respond.status` is required and is a JSON base-10 integer token with no
decimal point or exponent, from 200 through 599. All 1xx statuses are
invalid. `respond.body` is an optional string and defaults to an empty body.
After standard JSON string decoding, the body is sent as its UTF-8 bytes
without environment expansion, content encoding, normalization, or charset
transformation. Its decoded byte length must not exceed 64 MiB; larger bodies
are configuration errors.
`respond.headers` is an optional object mapping field names to non-empty
arrays of string values. Header names are case-insensitive and duplicate names
are invalid. Values use the existing response-header validation and
environment expansion rules. The managed names rejected by the existing
resolver are `Connection`, `Proxy-Connection`, `Keep-Alive`,
`Transfer-Encoding`, `TE`, `Trailer`, `Upgrade`, `Content-Length`,
`Proxy-Authenticate`, and `Proxy-Authorization`.

A 3xx response with a `Location` header is a redirect. More precisely, Kubio
calls a response a redirect only when its status is 300 through 399 other
than 304 and it contains at least one `Location` value. Kubio does not add a
separate redirect option. `Location` is validated as an ordinary response
header, may be relative or absolute, and is emitted exactly as configured;
Kubio never parses, normalizes, follows, or rewrites it. A 3xx response
without `Location` remains an ordinary generated response.

`respond` is valid only directly on a route. It cannot be combined with
`target`, `backend`, `timeout`, `tls`, request `headers`, `response`, or
`rewrite`. It conflicts only with `strip:true`; explicit `strip:false` is
allowed and ignored. The existing site rule requiring exactly one site-level
`target` or `backend` remains unconditional. A responding route may omit
route-level upstream fields; inherited target/backend, timeout, TLS, and
request headers are ignored and no upstream is contacted. The site-level
response policy is applied first, then `respond.headers`; `respond.headers`
wins except for Kubio-managed fields. Routes may continue to use `methods` and
`match` to select a generated response.

Strict JSON parsing rejects nulls, non-objects, unknown fields, aliases,
duplicate keys, missing status, invalid status, invalid body types, invalid
header names or values, and empty header arrays. `respond` is not valid at
site or backend level. The existing server-wide `OPTIONS *` handler runs
before site and route selection and is never intercepted by `respond`.


3. Response behavior

Kubio evaluates the route normally, then emits the configured status, headers,
and body instead of selecting or contacting an upstream. The request method,
query, and path do not alter the configured body. A body is required to be
empty for 204, 205, and 304; configuring a non-empty body for any of these
statuses is invalid. For a HEAD request, Kubio emits no body regardless of
the configured body and records zero response bytes. For other allowed
statuses, Kubio applies headers, commits the configured status, and writes
the exact body bytes once. If a managed implicit header is absent, the
standard `net/http` behavior applies.

Generated responses participate in the existing access log with their actual
status and bytes. The v0.21 request ID, when enabled, is applied to generated
responses with the same ownership and commit rules as proxied responses.


4. Reload and failure behavior

Kubio validates and compiles generated responses while constructing a
generation. Invalid configuration terminates startup and, on reload, is
logged while the current generation continues serving unchanged. Valid reloads
publish atomically without downtime; in-flight requests retain their
generation's response behavior.


5. Performance constraints

Response bodies and headers are validated and prepared once per generation.
The request path emits the selected route's precompiled response without
reading configuration or contacting an upstream. Routes without `respond`
retain the existing proxy path.


6. Deferred scope

The existing site response-header policy behavior for `respond` routes is
defined in this specification and is not deferred. Only new policy mechanisms
for Kubio-generated or intermediate responses remain deferred.

The following remain unresolved and move to v0.24:

- Custom bodies for Kubio-generated errors.
- Metrics, configurable log sinks/formats, and health/admin/reload endpoints.
- Forwarded and PROXY protocols.
- Client certificates, mutual TLS, TLS passthrough, configurable TLS policy,
  ACME, multiple listener certificates, and listener SNI certificate
  selection.
- Rate limiting, authentication, compression, caching, service discovery,
  response trailers, conditional response headers, request-header policies,
  adaptive retry policies, and policies for Kubio-generated or intermediate
  responses.
