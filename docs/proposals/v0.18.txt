Kubio kubio.json v0.18 Proposal
Status: Under review
Base: v0.17


1. Scope

v0.18 adds timeout controls to direct site and route targets. It covers the
connection, response-header, and response-body phases that are not controlled
by a named backend's timeout settings. Named-backend timeout behavior remains
unchanged.

This version does not add adaptive backoff, HTTPS upstream CA/SNI settings,
advanced route conditions, client-facing TLS, observability, administration,
routing actions, gateway features, additional header policies, or any other
deferred v0.17 item. Those items move to v0.19.


2. Configuration

A site or route may add a `timeout` object when its effective upstream
selection is a direct `target`:

    {
      "listen": ":8080",
      "sites": [{
        "hosts": ["example.com"],
        "target": "http://app:3000",
        "timeout": {"dial": "2s", "header": "5s", "body": "30s"},
        "routes": [{
          "path": "/slow",
          "timeout": {"header": "10s", "body": "1m"}
        }]
      }]
    }

The `timeout` object contains one or more of exactly `dial`, `header`, and
`body`. Each value is a positive, case-sensitive, untrimmed Go duration no
greater than 24 hours. Environment expansion is not supported. The object
must not be null or empty. Unknown fields, aliases, non-string durations,
invalid duration strings, zero or negative values, values above 24 hours,
duplicate keys, and null members are configuration errors.

`dial` limits connection establishment, including the TLS handshake. `header`
limits waiting for response headers after the connection is established.
`body` limits response-body streaming after response headers are received.
Each phase has its own duration; the settings are not a single total deadline
and do not limit time spent in another phase.

A site `timeout` applies to the site's direct target. A route without its own
`timeout` inherits the site's timeout when the route uses the site's direct
target. A route with its own `timeout` replaces the inherited object. A route
that selects its own direct `target` uses its own timeout or the default when
omitted. A route selecting a named `backend` has no direct-target timeout and
must reject `timeout`; the same applies to a site selecting a named backend.
The effective selection is determined after applying the existing site/route
target and backend rules.

The default direct-target values remain the v0.17 defaults: `dial` is 5s,
`header` is 30s, and `body` has no deadline. An omitted member uses its default
independently. A configured `body` timeout does not alter request retry
deadlines or named-backend timeout settings.


3. Direct request behavior

For a direct target, Kubio creates a transport with the effective `dial` and
`header` values. The direct request uses a child context whose deadline is
replaced or extended as necessary for the configured phases; client request
cancellation always wins. A dial timeout or response-header timeout produces
the existing proxy-generated 504 behavior. The target URL, header policies,
request forwarding, and response forwarding remain unchanged.

After response headers arrive, a configured `body` deadline starts. The
response body is wrapped so every read and close observes that deadline. A
body read that reaches the deadline returns a timeout error, and Kubio emits
the existing proxy error response behavior if the response has not already
been committed. A body timeout after response bytes have been committed
terminates the upstream body stream and cannot rewrite the client status or
headers. Client cancellation closes the body and wins over the body timeout.

An omitted `body` member leaves response-body streaming unlimited, preserving
the existing behavior. Body timeout state is local to the direct proxy
request; it does not alter another request or a named backend.


4. Retry and response semantics

Direct targets do not use named-backend status retries. A timeout in any direct
phase is not retried by v0.18. Existing route/site response header policies and
error handling remain unchanged. The `body` deadline begins only after the
upstream response headers have been obtained, so it does not consume header
timeout time.

The configured timeout values are captured by a router generation. A reload
does not change timeout behavior for an in-flight request; subsequent requests
use the new generation.


5. Validation and reload

Timeout objects are parsed and validated before a router generation is built.
A syntactically valid timeout on a backend selection is still invalid because
direct timeouts are not backend options. Startup errors terminate the program;
reload errors are logged and retain the current generation. A valid reload
publishes the complete replacement atomically without downtime.


6. Performance constraints

Direct targets without a configured `body` timeout retain the existing
response-body path and do not allocate a body deadline wrapper. A configured
`body` timeout adds one per-request wrapper and one timer/deadline mechanism;
it does not add work to named-backend requests. No request-path config read,
global lock, goroutine per request, or unbounded timer queue is introduced.


7. Deferred scope

The following remain unresolved and move to v0.19:

- Adaptive retry backoff policy extensions.
- HTTPS upstream CA, SNI, and certificate verification settings.
- Client-IP and other advanced route conditions.
- Multiple certificates, SNI certificate selection, ACME, redirects, mutual
  TLS, TLS passthrough, and configurable TLS policy.
- Configurable logs, request IDs, metrics, health/admin/reload endpoints.
- Forwarded/PROXY protocols, URI rewrites, redirects, fixed responses, and
  custom error bodies.
- Rate limiting, authentication, compression, caching, service discovery,
  response trailers, conditional response headers, request-header policies,
  and policies for Kubio-generated or intermediate responses.
